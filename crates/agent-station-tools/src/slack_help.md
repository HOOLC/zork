Forward one Slack Web API method using `slack.<official method name>`. Put `connect_id` and all native Slack parameters directly in `arguments`; there is no nested `method` or `arguments` wrapper. The runtime removes only `connect_id` and uses that configured connection's token. Caller/session identity is supplied by the runtime, not by these parameters.

Use `slack.connections` to obtain configured connection IDs. An unknown, disabled or unconfigured connection fails; there is no implicit current connection or fallback. Do not supply `token`. Slack determines whether the connection can perform the requested operation; this tool does not discover scopes or maintain an API allowlist.

For example, `slack.chat.postMessage` accepts `{"connect_id":"work","channel":"C123","text":"Hello","thread_ts":"123.456"}`. `slack.conversations.replies` accepts `{"connect_id":"work","channel":"C123","ts":"123.456","cursor":"...","limit":20}`. `thread_ts` belongs to the reply operation; `ts` selects the thread when reading replies. Preserve Slack timestamps and IDs as strings.

Parameters are transmitted as POST form values: strings stay strings; objects, arrays, numbers, booleans and null are JSON-encoded. When an official argument requires a comma-separated string, supply that string; the tool does not guess or normalize it. Additional fields, Blocks, metadata and nested structures are not filtered. Consult the method-specific official reference linked below for accepted parameters and their semantics.

The returned JSON body is Slack's response, including `ok`, `error`, `warning`, message IDs and `response_metadata`. `ok:false` or a non-success HTTP status makes the tool fail without discarding the body. Pagination is explicit: pass `response_metadata.next_cursor` unchanged to the next call on the same connection and target. A short page alone does not establish that there are no more results. The tool neither follows pages automatically nor combines or truncates histories.

For file uploads, call `slack.files.getUploadURLExternal` with the filename and byte length, upload the bytes with an ordinary HTTP-capable tool to the returned `upload_url`, then call `slack.files.completeUploadExternal` with the returned file ID and destination. The binary upload is not a Web API method; do not put a local file path into an API argument expecting file data. There is no legacy upload shortcut.

For example, complete a threaded upload with `slack.files.completeUploadExternal` arguments `{"connect_id":"work","files":[{"id":"F123","title":"Report"}],"channel_id":"C123","thread_ts":"123.456"}`. The completion API requires a `files` array, not a top-level `file_id`; the reply field is `thread_ts`, not `ts`. Without a channel destination the file remains private. Check the returned `ok` before treating the file as shared. See [Slack upload completion reference](https://docs.slack.dev/reference/methods/files.completeUploadExternal/).

No automatic retries are performed, including after 429, server errors, disconnects, or cancellation. Slack failures such as `missing_scope` and `not_in_channel` remain visible. A `slack_delivery_unknown` transport error means the effect may already have occurred; inspect the destination before deciding to repeat a write. Request and response bodies are bounded to 1 MiB; request smaller pages for large histories. The runtime's normal asynchronous waiting and cancellation rules apply.
