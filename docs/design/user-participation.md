# 业务工具中的用户参与

业务工具拥有完整的用户参与流程，包括卡片、卡片发出的请求、输入处理、业务执行与结果展示。通用交互基建只提供注册和管理逻辑，不包含业务信息。

## 调用方式

Agent 调用原本要用的业务工具，调用参数就是预填数据。业务判断需要用户参与时，注册自己提供的交互入口并保持原调用 pending。注册通知只给同一 Agent Session 提供请求引用、原调用关联和归属信息。

Agent 用 Chat 工具发布已有请求引用，对应业务提供卡片。OAuth 也可随 chat.post_message 直接发送到指定 Chat，由这次发送调用持续等待连接结果；登录适配器负责凭据、回调和连接保存，不再增加登录专用工具或一次额外的发布通知。卡片的操作进入对应业务的客户端 core 接口，由业务接收、校验并处理输入，接续原调用，更新自己的卡片内容并返回工具结果。Chat 订阅不参与原调用的响应回传。

没有独立的交互创建／等待工具；Chat 不另建业务表单入口。实际工具参数以源码和生成帮助为准。

## 职责

注册管理维护业务入口的注册、查找、身份、归属、原调用关联以及条目的撤销和清理。它不保存或解释卡片字段、预填值、用户输入、业务回执和结果，也不定义统一的表单、审批或登录协议。

卡片内容、动作及其请求协议、接收输入、校验、提交值合并、回执、等待接续和结果呈现都属于对应业务。并发提交是否接纳、何时允许修改、如何去重和恢复，由业务根据自己的操作语义决定。业务可以复用组件、存储和网络能力；复用不把这些业务职责划给交互基建，把业务载荷改成不透明 JSON 也不等于完成边界分离。

业务归属与 [core/UI 边界](client-core.md) 同时成立：客户端业务模块位于 core，负责卡片操作、请求、状态、校验和恢复；平台 UI 只呈现业务的只读投影、采集输入和执行平台能力。卡片归业务不意味着让 UI 构造 HTTP 请求或保存第二份业务状态。

以创建 Agent 为例，创建一律需要用户参与：Agent 业务生成带预填值的卡片并注册入口；注册管理提供可查找、可撤销的引用。用户提交后，Agent 业务接收输入、校验配置、创建 Agent、更新卡片并完成原调用。修改 Agent 时由该业务保留局部修改语义；完整、已授权且不需要用户参与的修改直接执行。

### 面向用户的卡片

业务按用户需要作出的决定组织卡片，不将工具参数 schema 直接展开成配置表。优先呈现本次需要补充或确认的内容；修改时说明对象并突出本次改动，其余设置可展开查看，收起不丢失预填值或输入。模型、权限与技能使用可辨认的选项，不要求用户编写 JSON 或辨认内部路由标识。无法取得名称时保留可区分的真实引用，不编造身份。

按钮说明将发生的业务动作，等待状态说明下一步由谁完成。登录卡片用用户能执行的步骤说明授权过程；操作结束后显示对应业务结果，不能只以 HTTP 请求成功代替完成。

## 执行、取消与恢复

每项注册关联实际业务 invocation 及稳定槽位。原工具 Future 位于现有执行链中；没有额外业务 Workflow 或等待工具。业务等待期间不持有 Agent 资源锁或数据库事务。工具声明可等待用户，既有调用运行时依据该能力管理等待；对应业务 RPC 在 Mesh 上先完成订阅握手，再等待执行结果，普通连接建立超时不限制用户操作时间。

源节点在发送业务调用前持久登记 invocation 和目标。传输回执暂时未知时，业务沿同一调用恢复，使用自己保存的输入和回执，不提前返回成功或重新执行。工具结束后清理其残余注册，完成登记不将原调用标记为取消，原业务回执仍可恢复。源调用丢失时沿原身份处理清理；注册条目的撤销不替代业务取消，业务须结束自己的等待，并在实际提交时核对取消状态。取消不等待该操作的去重锁。

Agent 创建／修改业务将业务效果、调用回执及最终卡片事件在同一事务提交。重复 HTTP 请求、重新发卡片和重复用户响应不创建第二次业务效果。用户响应与取消竞争时，由业务依据权威记录和已提交结果处理；已完成效果不被取消覆盖。

进程重启不能恢复任意 Rust Future。业务恢复须明确结束已经失效的等待；已接受但无法确认效果的操作保留 unknown，禁止自动重放。历史消息保留在源日志中，移除旧工具和旧卡片协议时不保留兼容执行分支。

## 私有交互与登录

登录业务拥有登录卡片及其请求、链接、验证码、回调、Provider 轮询和凭据保存，在原业务调用内通过已有授权服务推进。对应私有接口及客户端操作也由登录业务提供；交互注册管理不承载这些内容。同一 Profile 的新登录取代并取消旧尝试，请求身份独立不要求这些登录尝试并存。

登录业务的挑战和回调仅经过认证的私有接口及内存通道，不写入普通消息、Agent 通知、公开事件或客户端持久提交队列。凭据实际保存才表示完成；过期、确定失败及保存结果未确认分别表达，不能根据错误文案猜测。其他业务的外部交互采用自己的内容和操作语义。

## 消息与客户端投影

业务通过 append-only Chat 消息发布卡片及后续内容，卡片引用已有注册。业务拥有卡片内容及其归并语义，Chat 提供既有消息能力。core 可以更新原消息的派生缓存；结果先到时持久暂存，后到请求先归并再呈现。同步游标始终按原始消息流推进。

已连接客户端按消息源的变化接收更新；业务直接发布的结果也必须触发通知，不依赖 Agent 是否订阅 Chat。通知只提示追赶持久源，不包含私有登录输入，也不引入逐卡片轮询。

绑定卡片与后续事件投递保留持久快照、跨节点发布凭据及事件序号。不同 Chat 中的卡片可以引用同一业务交互；迟到卡片由业务给出最新内容。业务决定结果卡片保留哪些公开输入，秘密不进入消息。请求入库、暂存结果归并及对应分页水位在一致边界提交；重复页、迟到阶段和重开不能回退卡片或重放效果。UI 不维护第二份业务列表，也不根据正文或邻接位置猜测关系。

注册引用、业务调用、用户提交及消息事件各有自己的身份作用域；引用本身不授予业务权限。业务卡片及动作采用版本化合同，业务归属和注册引用随请求及后续事件保留；结果先到的暂存及后续归并同样校验这两项身份。未知版本或未注册的业务只读，不分派动作。具体业务协议不进入注册管理合同。

## 验证边界

分别核对注册管理的依赖和合同、业务卡片从用户输入到原调用结果的完整路径，以及各端只读呈现。注册管理不能依赖具体表单、用户提交或业务结果类型；业务回归通过不证明这一边界成立。

业务接续使用生产创建／修改 Agent 和登录入口验证，观察同一 invocation 的实际业务效果、错误修改、局部更新、重复提交、拒绝、取消与恢复。业务的并发输入现象按该业务的语义判断，不能由此推导交互基建的通用提交策略。测试入口按 [验证 skill](../../.agents/skills/zork-validation/SKILL.md) 选择，执行结果随任务保存。
