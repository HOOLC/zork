# 共享文件 CAS 审计与回收

此流程处理内部目录曾被发布后留下的网络快照；[文件权威与退役约束](../design/shared-files.md)仍然适用。执行历史、工作区和 Chat 附件原文件始终保留。不要根据目录大小或重复文本直接删除 CAS、SQLite 行或 pin，也不要在备份上启动带原节点身份的第二个 Mesh 实例。

## 只读预览

明确每个运行实例的数据根与生命周期所有者。Station、访问客户端和停用的旧数据目录分别审计；运行版本与源码版本分别记录。节点停止时，数据库仍可能保存尚未退役的 source，这不表示它此刻正在发布。

从仓库运行：

```sh
python3 scripts/audit-file-cas.py --data "$ZORK_DATA" --compare-history --output "$ZORK_REPORT"
```

访问客户端的 `--data` 使用其 transport 数据根。输出放数据目录之外的私有位置，不提交到 Git。脚本只读 SQLite 的一致快照，并检查 CAS 文件；不打开 Synch 引擎、不联系对端、不退役 source，也没有 apply 模式。参数和报告字段以 `--help` 和脚本为准。若只读数据库无法打开，先确认 WAL、目录权限和运行所有者；不要绕过 WAL 强读一个可能陈旧的数据库。

报告区分当前引用、pin、尚在保留期和满足内容 GC 条件的对象。退役预测只撤销本机旧 source；对端的引用、其它持有者的 pin 和未结束的保留期继续阻止回收。已安排释放的 pin 在引擎真正释放前仍按保留处理。历史前缀比较只输出路径和数量，不输出日志正文；相似大小或相同开头都不替代完整字节比较。

审查必须同时看引用归属、是否有原文件、备份可用性和当前运行版本。CAS 文件长度及文件系统分配块都不是 APFS 独占物理空间，不能据此承诺释放量。在线目录与数据库不是共同原子快照，报告不构成可稍后照单删除的清单。

## 经审查后执行

1. 固定通过本任务验收的完整节点产物，按原有 dev/release 策略选择安装目标。核对候选实际使用的业务数据库与已有数据一致；名称或路径跨版本变化时，先在隔离备份上验过部署迁移，不能把新建空库当作恢复成功。确认没有仍需保留的旧共享链接；本方案不会恢复已放弃的旧链接。
2. 按原生命周期所有者正常停止目标 Station，等待真实进程结束。关闭任何使用同一数据根的访问客户端；不因维护重新 join、轮换身份或重新创建 Session。
3. 在私有位置备份完整数据根与原安装产物，保留配置、身份、业务数据库、WAL、原文件和 CAS 的一致组合。备份期间不得有写入；核对摘要及可读性后才继续。不要只备份二进制，也不要覆盖原数据。确认维护窗口内不接收新的执行任务。
4. 通过原生命周期所有者，用候选产物启动**原位置、原身份**的节点。启动流程会先发布旧业务 source 的撤销，再解除本机 source 角色；原目录不动。分别在本机审计及已连接对端的目录视图确认撤销生效。对端离线、仍运行旧发布器或保留其它引用时，先处理对应节点，不能手删本机元数据假装收敛。
5. 重跑只读审计。保持引擎现有保留配置，让正常维护循环在期限到达后回收符合条件的内容。不要改系统时钟、缩短保留期、强删 operator/replica pin，或用预测时间冒充真实到期。`--at` 只用于审查未来的条件变化。
6. 回收前后核对执行历史与权威附件的摘要，实际打开已有 Session、读取旧消息附件，并验证新共享文件和跨节点文件发送。再次审计以确认对象数量变化，分别记录逻辑字节、CAS 文件变化与实际磁盘变化。

若发现不应撤销的引用、备份不完整或验收失败，停止维护并保留现场。恢复需要完整、同一时间点的备份；已有新执行或新消息时不能直接用旧备份覆盖，应先保存新增历史并制定单独恢复方案。不要混合旧数据库和另一时点的 CAS。

## 模型上下文不在本流程内

`provider_input` 是模型请求的计数与响应标识诊断，不是全量输入副本。`provider_context` 保存供应商返回项，在相同 profile/provider/model/API 的后续请求和重启回放中复用；其中可能有推理数据或供应商要求原样返回的内容。两者都不是 CAS 回收的替代删除目标。任何上下文瘦身应单独验证对应供应商的模型回传、工具接续和重启语义。
